# 第二份参考资料核验与选型修订

日期：2026-09-14。作者：主 Agent。输入：[第二个参考资料.md](第二个参考资料.md)。

## 一、结论：新资料有实质增量，应修订上一轮排序

**这份资料不只是重复上一轮，新增的三个项目值得纳入比较。** 核对源码后的结论是：

1. **Claude 侧优先候选改为 `es6kr/claude-code-sessions`。** 它有 MIT 许可、独立 TypeScript Core、真实 Web 编辑链和类型感知的内容修改，比 llm-lens/didvc 更适合作为改造起点。
2. **不能据此宣布“ClaudeBackend 已经做好”。** 它仍以一条消息中的首个可编辑块为目标，缺少普通编辑的可靠提交链，并存在同 UUID 读取/写入不一致。
3. **XiaoZhi 的项目确实覆盖 Claude + Codex 编辑。** 所以此前“没有双引擎候选”的判断应限定为第一轮六个项目。新增项目技术覆盖较广，但未授予明确开源复用许可，且运行时保护明显偏 Windows。
4. **Codex projection handling 是真实需求。** 官方源码确认分页 UI 使用增量 SQLite 投影。不过“改 JSONL + 删除三个表中当前 thread 的行”不是跨版本、跨平台、共享历史都适用的完整方案。
5. **session-porter 适合参考 Adapter 接口，不适合无损编辑保存。** 它是格式转换/迁移器，会重建记录和工具关系，SQLite 注册也只是 best-effort。

因此，新建议为：**优先评估 es6kr 的 Claude Core/界面，结合 coldxx 的 Codex 编辑思路，自行实现可恢复写入、来源定位、共享锁与版本化投影适配。** 不接受“一两天即可完成可靠三引擎编辑器”的工期结论；本项目当前仍以 Claude + Codex 为目标。

## 三、es6kr：值得提升优先级，但不是完成态写入后端

### 3.1 新资料中得到确认的部分

项目是 pnpm monorepo，版本声明为 0.5.5，包含 Core、Web、MCP、VS Code 等包；Core 为 TypeScript，运行时依赖 Effect。[E1]

完整编辑链确实存在：

```text
SessionViewer.svelte 的编辑状态和保存操作
    → Web API：PATCH /api/message?project=...&session=...&uuid=...
    → session.updateMessageContent(...)
    → 读取 JSONL、修改目标 content、写回
```

后端失败会映射为 404/422，前端保存成功后刷新服务器数据，并非只有未连接的编辑按钮。[E2][E3]

`updateMessageContent` 允许 `user/human/assistant`，按以下优先级选取**第一个**目标：

1. `text` → 改 `text`；
2. 没有 text 时，`tool_result` → 改 `content`，保留 `tool_use_id/is_error`；
3. 再没有时，`thinking` → 改 `thinking`，保留其余字段；
4. 只有 tool_use、没有可编辑目标时拒绝；
5. 其他情况追加 text block。

非目标 blocks 和消息外围字段会保留，后续消息不被有意截断。这确实比 llm-lens/didvc 的整条 content 坍缩更合理。[E4]

仓库已有相应的 tool_result、thinking、混合块和工具配对测试。本轮只阅读了这些测试。[E5]

### 3.2 新资料低估的限制

| 限制 | 源码依据 / 影响 |
|---|---|
| 不是任意 block 编辑 | API 只有 UUID + newText，没有 block locator；同条消息第二个 text 无法单独指定，text 存在时也不能转而选 thinking |
| 普通编辑无完整提交保护 | `crud.ts:292–293` 全文件 stringify 后直接 `fs.writeFile`；该路径没有原文备份、临时替换、revision/hash 检查或官方写入者协调 |
| 读取与写入的重复 UUID 策略相反 | `dedupeMessagesByUuid/readSession` 保留最后出现的 UUID；`updateMessageContent` 用 `findIndex` 修改第一个 |
| 字符串形状会变化 | 原 content 为字符串时，保存后变成 text block 数组；可能合法，但不是保持原表示不变 |
| thinking 签名不被重新生成 | 保留 signature 字段只能说明字段未丢失，不能证明改变 thinking 后签名仍有效 |
| 文件格式仍会整体重序列化 | 未修改记录的值通常保留，但空白/换行不是字节无损；严格解析避免静默丢弃坏行，不等于保存具原子性 |

其中重复 UUID 存在一个可由源码直接构造的反例：

```text
原文件：同 UUID 的旧记录 A、较新的记录 B
readSession：展示 B
updateMessageContent：改 A，返回 success
再次 readSession：仍展示未改的 B
```

这不是本轮浏览器实测，但读写策略冲突在源码中明确存在。[E6][E4]

**评价：提高为 Claude 改造首选；采用前应先补 block locator、统一重复记录策略、备份/冲突/原子写和写后复读。** “类型感知”是一项进步，不等于全部图关系、恢复、并发都已解决。

## 四、Codex SQLite projection：新资料基本正确，但需要限定适用范围

### 4.1 官方源码确认了什么

当前核对的 Codex commit 仍为 `d76109773497850ed2699f2816e3f7b1867d0c14`。

`thread_history.rs` 的确操作 `thread_items`、`thread_turns` 和 `thread_history_projection_state`；checkpoint 记录下一 byte offset 与 ordinal，投影和 checkpoint 在 SQLite 事务中提交。[C1]

`materialize_to_sqlite` 从已记录 offset 继续读取，不是每次重新读取所有旧内容：

- checkpoint 不存在时从 0 开始；
- 新文件比 checkpoint 短时会报 `durable rollout shrank before projection`；
- 如果在旧前缀内做等长替换且没有新增字节，这条增量路径可能直接返回，不重建旧投影。

因此，“JSONL 内容已改，而分页 UI 仍显示旧投影”有直接源码依据。[C2] 这与上一轮“模型上下文仍从 rollout lineage 重建”的结论并不矛盾：**展示投影和模型有效上下文是两条不同的数据处理链**。

### 4.2 为什么不能固化成“删除三表即可”

1. **表集合随版本变化。** 本次官方 `delete_thread` 除上述三表，还处理 `thread_realtime_items`。对支持实时记录的版本，需要核对完整依赖，不能写死三表就是永远正确。[C1]
2. **重建不等于修复所有源日志问题。** 坏 ordinal、共享前缀的字节边界、压缩格式等仍需先处理源记录的完整性。
3. **只清当前 thread 并非所有场景成立。** 若改动一份被其他 rollout 引用的历史前缀，影响范围可能超过当前 thread；这也是第一版不应直接覆盖共享前缀的原因。
4. **清 UI projection 不会重算 compaction summary。** 也不会自动更新已加载的内存模型历史。
5. **需要可恢复、按版本的失效计划。** 不删除整个历史数据库；应先确认当前使用的 DB 路径/schema、备份，再处理准确的受影响记录。

GitHub #38792 和 #43451 确实描述了 projection 卡住而 rollout 完整的现象，但它们是针对具体 CLI/Desktop 版本的用户报告，不能单独当成“官方承诺所有版本删三表即可”的证据。[I1][I2]

## 五、XiaoZhi：双引擎能力真实存在，但仍须看具体写入路径

### 5.1 确认存在的技术能力

- Claude：按 `targetId + locator` 定位字符串、text、结构字段、JSON、附件或记录字段；使用 `expectedText` 和 `sourceHash`，编辑前保存原文件，保留未修改记录的 raw 内容。[X1]
- Codex：先获取目标锁，再比对 source hash，备份 rollout 和历史 DB，改写后重读解析，最后让目标 projection 失效；失败时尝试恢复原 rollout。[X2]
- 历史 DB 备份调用 `node:sqlite.backup`，不是简单复制热 WAL/SHM；三表失效使用 `BEGIN IMMEDIATE` 和 thread_id 条件。[X3]
- Claude 的 preview/apply/restore HTTP 路由实际连接到相应实现；不是仅有 API 文档。[X4]

所以，**它是新增的、真正具双引擎正文编辑能力的参考实现**。第一轮只研究六个候选时没有发现，不应继续作全局性的“没有双引擎项目”断言。

### 5.2 不能把 DATA-SAFETY 文档全部当作实现证明

| 项目 | 具体限制 |
|---|---|
| 平台 | README 明确面向 Windows；目标锁借助 `powershell.exe` 和 .NET FileStream 字节区间锁 |
| macOS/Linux | `withTargetSessionLocks` 在非 Windows 且锁目录存在时拒绝；目录不存在时直接进入操作，不代表已经获得等价保护 |
| 共享锁协议 | 官方确有 `thread-writer-locks`，但当前官方还使用 `.coordination.lock` 协调锁文件创建/删除/发布；跨版本/跨平台需要验证协议一致性，不能只复制目录名 |
| Claude 写后校验 | `applyClaudeMessageEdits` 写完即返回基于内存字符串的 hash；此函数未见文档声称的写后重新解析/失败自动恢复链 |
| Claude 恢复 | 使用 `copyFile(payload,target)`；不能把 Codex 路径的原子恢复保证套用到它 |
| 不支持的 projection schema | `invalidateThreadHistory` 返回 `available:false`；Codex apply 路径没有将该结果自动升级为失败 |
| 新格式 | 未在该项目源码中找到 `history_base`、共享前缀字节边界或 `thread_realtime_items` 的处理 |

依据：[X1][X2][X3][X5]；官方锁实现见 [C3]。

这里需要修正上一轮一个容易过度概括的说法：**不是任何第三方锁都无法与官方协调。** 如果目标版本提供同一写入者协议，并且平台实现正确兼容，就可以实际协调；但独立工具私有锁、mtime 启发或简单 hash 比较不能被冒充为这种能力。

### 5.3 许可直接影响“能否作为基底”

README 明确写明目前未声明开源许可证，公开可见不等于允许复制、修改、再分发或商业使用。[X6]

因此，本次仅作静态设计研究，不复制其实现到新产品，也不把“可以先运行测试/直接 fork 长期开发”视为已经获得许可。若希望直接采用，需要先获得作者明确授权；否则从有许可的官方源码、文档和通用机制独立实现。

## 六、session-porter：适合作为迁移器，不应当用作编辑器的保存模型

其 `AgentAdapter` 的发现、读取、写入及工具映射接口确实存在，MIT 也已核对。[P1]

但实际 writer 是**重新生成另一份原生记录**：

- Claude writer 新建 session UUID、消息 UUID、父链，重建 text/tool blocks，并可能补造 `[No output captured]`。[P2]
- Codex writer 新建目标文件、合成事件/正文表示及 turn 外壳，并填写默认 provider、版本等信息。[P3]
- Codex SQLite/index 注册在 `try/catch` 中 best-effort 执行，即使失败也可能返回 `success:true`。所以“保证 resume 能找到”比实现证据更强。
- 同引擎 transfer 会明确清空源 ID 以生成新会话；`raw` 模式仍会清理/配对工具项，不是源 JSONL 字节直通。[P4]

**建议仅借鉴 Adapter 边界、发现方式和显式迁移模式。** 新编辑器仍应保留原始记录，按定位器 patch；不能经过 portable representation 后再回写并声称无损。

## 七、更新后的选型建议

| 目标 | 更新后的建议 |
|---|---|
| Claude 单引擎编辑基础 | 优先 es6kr；先修可靠提交、任意 block 选择和重复 UUID 一致性 |
| 有明确许可的 Codex 编辑参考 | 继续采用 coldxx 的 target 映射/备份思路，补版本化模型历史、projection 与写入者协调 |
| 双引擎完整功能的设计对照 | XiaoZhi 值得深入对照，但许可和 Windows 依赖使其不能直接作为当前 macOS 项目的默认基底 |
| 跨引擎导出/迁移 | session-porter；与原地编辑作为独立功能维护 |
| 完整 Web/MCP/VS Code 多端产品 | es6kr monorepo 比 coldxx 巨型单文件 UI 更值得优先验证 |
| 只做本地 Web，沿用现有使用体验 | 仍可保留既有 React/MUI 界面，提取经修正的 es6kr Core 思路和 Codex adapter；没有必要仅为 Core 强制改成 Svelte |

**我会把“Claude 侧先参考 llm-lens”修订为“先验证 es6kr Core”。** 如果确定需要现成 SvelteKit + MCP + VS Code 生态，优先考虑 fork es6kr；但不是零改动套上 Codex parser 就完成。

统一接口继续采用：`discover → load raw → project view → identify target → preview plan → coordinate writers → backup → apply → verify → repair/invalidate required projections → restore`。

需要增加 `CodexProjectionManager`，但它不是唯一新增模块。仍需解决：块级无损修改、身份与副本关联、共享 lineage、活动内存会话、压缩检查点、失败恢复和版本探测。

OpenCode 可以将来接入单独 Adapter，当前两引擎目标不因此自动扩成三引擎。新资料中的“一两天完成”没有构建/集成/恢复验证支撑，不作为工程承诺。

## 八、下一步建议验证的最小用例

1. es6kr：普通文本、混合 content、第二个 text block、工具结果、签名 thinking、重复 UUID、无效行；同时核对保存后 UI 与磁盘是否一致。
2. Codex：等长编辑已投影前缀、变长编辑、历史缩短、projection 缺失/落后、不支持 schema、实时表；对比官方分页 UI 与 model context。
3. 写入者协调：目标版本和平台的真实共享锁竞争、锁文件生命周期、预览后重新打开会话。
4. 恢复：模拟 JSONL 已替换但 projection 失效失败，核验原文/备份/投影的可恢复性。
5. 复杂历史：压缩窗口前后、已加载线程、共享前缀及多个相关线程，不能只测单个独立旧式 JSONL。

这些是下一阶段的验证计划，本轮没有执行。许可允许的项目可先在隔离目录做合成数据测试；不要用真实会话试错。
