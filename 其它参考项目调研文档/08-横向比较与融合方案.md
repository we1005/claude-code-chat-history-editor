# 横向比较与融合方案

调研日期：2026-09-14。作者：主 Agent。基于六份候选报告及 [官方机制核验](07-Codex与Claude会话存储机制核验.md)。

> **第二轮已更新**：新增 es6kr、XiaoZhi 和 session-porter 三个项目。Claude 侧优先级调整为 es6kr；“没有双引擎项目”仅适用于第一轮六个候选，不能再作全局结论。新增证据、具体缺口与源码链接见 [09-第二份参考资料核验与选型修订](09-第二份参考资料核验与选型修订.md)。

## 一、直接回答选型问题

**已找到真实的双引擎编辑实现，但“技术上能编辑”与“有许可、可可靠地作为长期产品基底”需要分别判断。**

- **Codex：首选研究和提取 `coldxx`。** 它已经具备 turn/record 编辑、相关文本副本同步、备份和临时文件替换；在合成测试中能修改中间消息并保留后续记录。
- **Claude：第二轮优先选择 `es6kr/claude-code-sessions` 作为改造候选。** 它有 MIT、独立 TS Core、类型感知编辑及 Web 链路；但需补任意 block 定位、重复 UUID 一致性和可靠提交。llm-lens/didvc 降为辅助参考，不能照搬其压平 content 的 writer。
- **双引擎：XiaoZhi 的项目确实有 Claude/Codex 编辑链、备份和 Codex projection 失效处理。** 但无明确开源复用授权、偏 Windows，且部分安全文档强于实际实现，不能直接当成当前 macOS 项目的可用开源基底。
- **Adapter 参考：session-porter 值得研究，但它是转换/重建工具。** 不应用其 portable representation 作为原地编辑保存格式。
- **Tauri Manager 与 VS Code 扩展适合借鉴诊断、索引和管理功能。** 它们没有普通正文编辑能力；Tauri 版本的恢复/导入还存在计划与执行脱节。
- **CSM 适合研究有效历史重放。** 它没有正文编辑，未发现明确项目许可证，且依赖未固定 commit 的相邻 Codex 内部源码，暂不作为直接复制的代码来源。
- **推荐融合方式：独立统一界面 + 共享文件提交层 + 两个专用引擎适配器。** 复用经过验证的模块和交互，不把六个项目整体拼起来。

如果必须选一个有明确许可的完整多端工程，**第二轮应优先验证 es6kr，再加入 Codex adapter**；如果只做本地 Web，也可保留既有 React/MUI 界面，提取经修正的 es6kr Core 与 coldxx 思路。长期架构仍是薄的统一工程与分引擎适配，不是原样拼接多个单体后端。

## 二、评价口径

本项目主要场景是：定位已有 Session，编辑用户或助手的某个正文块，保持 session 身份和后续历史，随后能够正确继续使用。

必须区分：

| 操作 | 含义 |
|---|---|
| 原地编辑 | 修改选定字段，保留后续记录和原 session 身份 |
| 删除 | 删除指定消息/块，并处理它的引用关系；不必然删除全部后续 |
| 截断 / 回退 | 让某个位置之后的历史被删除或失效 |
| fork / clone | 创建新身份的分支或副本 |
| repair | 修复特定结构、索引、Provider 或执行状态，不代表可以改正文 |
| compact | 用摘要/快照等机制改变模型有效上下文，不是无损消息编辑 |

以下“支持编辑”主要指 **UI/存储层已有实现**。六份报告都没有完成“修改真实客户端会话后，捕获下一次模型请求证明采用新正文”的端到端验证。

第二轮新增三个项目为主 Agent 静态源码核验，同样没有完成该端到端验证。

## 三、横向能力矩阵

| 项目 | 引擎 / 形态 | 用户与助手正文 | 后续记录 | 定位 |
|---|---|---|---|---|
| **coldxx** | Codex / Node CLI + Web | 支持 turn 路径级编辑和 raw record 编辑 | 普通编辑保留；rollback/truncate 会截尾 | **有 MIT 许可的 Codex 编辑参考** |
| **llm-lens** | Claude / Python Flask + Web | 支持，但列表 content 被压成单 text block | 有效 JSON 对象通常保留，坏行会丢 | Claude 浏览与语义参考较强，writer 要重做 |
| **didvc JSONL Editor** | Claude / Preact + Express | 支持，但整个 content 被替换成字符串 | 有效对象通常保留，坏行会丢 | 小型 UI 原型，不宜做可靠编辑核心 |
| **citizenll/csm** | Codex / Rust CLI + TUI | **不支持**；只改少量 meta/窗口字段 | 依操作而定；fork/compact/rollback 语义不同 | 有效历史重放与原生操作参考 |
| **fengchenzxc Manager** | Codex / Tauri + React | **不支持**；详情只读且有截断 | clone/migrate 保留消息，但不是正文编辑 | 多层状态诊断、操作计划与桌面壳参考 |
| **bimcc session-man** | Codex / VS Code 扩展 | **不支持**；编辑表单只针对 Provider | Provider 编辑保留后续字节 | 轻量索引、Provider 对账与流式处理参考 |
| **es6kr sessions** | Claude / TS Core + SvelteKit 等 | 支持首个类型感知目标；不能任意选 block | 普通编辑保留后续对象 | **新的 Claude 改造首选** |
| **XiaoZhi manager** | Claude + Codex / Web，面向 Windows | 支持字段/块编辑与预览应用 | 普通编辑保留，另有删除/截断 | 双引擎设计参考；许可与平台受限 |
| **session-porter** | Claude ↔ Codex / CLI | 转换并写新记录，不是原地 patch | 归一化/重建，不保证原始结构无损 | Adapter 与迁移功能参考 |

第一轮六个候选没有现成双引擎编辑；第二轮新增 XiaoZhi 已有该实现。仍不能把 coldxx 的 Anthropic-compatible 文本改写接口理解成 Claude Code 历史支持，也不能把 session-porter 的跨格式写入理解成无损原地编辑。

## 四、可靠性与复用成本

| 项目 | 已有保护 / 优点 | 关键缺口 | 许可 |
|---|---|---|---|
| coldxx | 消息编辑前备份、恢复、同目录 rename、mtime 活跃窗口 | 同文聚组有误合并/漏同步；空行定位错位；无跨写入者协调和版本校验；未覆盖现代 lineage | MIT |
| llm-lens | 发现、分页、子会话浏览、部分父链重连 | 混合块坍缩；嵌套内容编辑可能假成功；普通编辑直接覆盖、无原文备份；工具清理单向 | MIT |
| didvc | 简洁聊天 UI、默认文件备份 | 坏行丢失；混合块坍缩；备份失败仍继续覆盖；无链/工具校验和恢复 UI | MIT |
| csm | 内存先验证、调用原子写 helper、写后对账思路 | 无正文编辑；原子写依赖源码版本不固定；无普通备份/冲突保护；构建未验证 | 未发现明确项目许可 |
| Tauri Manager | dry-run/plan、备份、多存储诊断、部分进程检测 | 跨文件/SQLite 部分写；restore/import 无实际动作处理；写入清单不完整 | MIT |
| VS Code 扩展 | 首行流式替换、Provider 差异检测；health repair 有备份 | Provider 编辑无备份；多层非事务；固定 state_5 schema；没有正文/块定位 | MIT |
| es6kr | 类型感知地保留非目标块、严格 JSONL 读取、Core/Web/测试链路 | 普通编辑直接覆盖、无备份/版本保护；读最后同 UUID、写第一个；只选首个目标块 | MIT |
| XiaoZhi | 字段 locator、hash/预览、备份、Windows 目标锁、Codex 投影失效 | 许可未明确、锁缺跨平台适配、Claude 写后校验弱于文档、未覆盖共享前缀 | 未声明开源许可证 |
| session-porter | Adapter 接口、格式/工具映射、原生文件生成 | 有损重建、可补造工具输出、SQLite 注册 best-effort，不是历史编辑 writer | MIT |

“有备份”“有 rename”“能判断最近写入”是不同能力，不能合并成一个笼统的“安全 ✅”。尤其 **hash/mtime 复查 + 自己的锁仍不是与官方客户端之间的原子 CAS**。

相对成本判断：

- **最低成本的 Codex 原型**：coldxx，Node 内置模块即可运行，已有真实消息写入链。
- **最低成本的 Claude 简单文本演示**：didvc，但短代码不等于低成本达到可靠性目标。
- **Claude 产品功能与 Core 新首选**：es6kr；llm-lens 的 Python 单体和有损展示模型不再是优先路线。
- **最重的基底选择**：直接继承 CSM 的 Codex 内部 Rust 依赖，或把 Tauri Manager 扩成两引擎编辑器；与当前核心需求重叠不足。

## 五、对 ChatGPT 参考资料的纠偏

### 1. llm-lens 不等于“保持 UUID 就能安全 resume”

主 Agent 复核 `api_edit_message`：它读入可解析记录、替换目标 `message.content`、直接以 `open(..., "w")` 重写文件；没有调用 prose-only 限制，也没有普通编辑备份。[源码](https://github.com/jajanet/llm-lens/blob/307c31acb0c255d5c3aa6cb4a3001bfe21af11a0/llm_lens/__init__.py#L2977-L3041)

报告 01 的合成测试还发现工具配对孤儿及嵌套内容假成功。因此，可以保留“它实现了正文编辑与部分链修复”，不能保留“可直接作为安全恢复编辑器”的强结论。

### 2. coldxx 的多副本同步有明确适用条件

主 Agent 复核 `getSessionTurnEditPlan` / `updateSessionTurnMessages`：按同一推断 turn 中的 `side + 完全相同文本` 归组，再逐路径更新。[源码](https://github.com/outx-sec/coldxx/blob/9265318527336a9300f29584690c12a1d4e3cc31/src/core.js#L1156-L1263)

这个思路值得保留，但不是稳定消息 ID 的关联模型。不能让本来就不同步的副本继续漏改，也不能把同轮同文的两条独立消息自动合并。10 分钟保护是 mtime 启发式，不是官方会话锁。

### 3. didvc 的“实时同步”不是持续文件监控

报告 03 指出气泡保存只改浏览器内存，顶部保存才覆盖文件；页面启动后两次探测也不是 watcher。主 Agent 另核对到 README 的确有多处安装地址指向 `anthropics/claude-code-jsonl-editor`，而本次实际仓库属于 didvc。[README](https://github.com/didvc/claude-code-jsonl-editor/blob/7edc2d0f58db28b81e199a4ffa106d1e9ed96ff5/README.md#L54-L103)

### 4. CSM 的 rollout surgery 不是任意正文编辑

报告 04 确认它只实现 meta 和窗口提示两种文件改写。主 Agent 复核 Cargo 清单，三个 Codex 内部 crate 使用相邻目录 path dependency，未固定源码 commit，项目也没有声明 license 字段。[Cargo.toml](https://github.com/citizenll/csm/blob/130a9a788c285719f34583fffc2738ec5b0c86ef/Cargo.toml#L1-L27)

参考资料把它列为“部分正文编辑”容易误导；更准确的是“会话元数据与有效历史管理”。

### 5. Tauri Manager 的恢复按钮不能视为恢复实现

主 Agent 复核 `apply_operation`，其动作分派没有 `restore_file` / `preview_import`，未知动作落入空分支。即使生成计划、创建备份或改写全局文件，也没有完成目标文件恢复。[源码](https://github.com/fengchenzxc/Codex-Session-Manager/blob/724c8bc391634b2d83f09e4cf0cc5147894ae2d0/src-tauri/src/lib.rs#L1795-L1881)

### 6. 还需补上最新 Codex 的存储模式

六个候选的主要代码日期早于本次 Codex 官方 main 快照。官方已有 paginated history、共享不可变前缀和压缩 rollout；`thread/revert` 还可能更换物理 rollout 而保持 thread ID。**不能把这些候选对传统 JSONL 的测试，外推为当前所有 Codex 会话都可写。** 详见 [07 机制核验](07-Codex与Claude会话存储机制核验.md)。

## 六、推荐融合架构

```text
统一本地界面（项目 / 引擎 / 会话 / 消息 / 内容块）
  ├─ 完整消息流、搜索定位与上下文
  ├─ 正文编辑、原始记录、变更预览、备份恢复
  └─ 显示来源版本、可编辑范围、有效上下文状态
                       │
                SessionService
         ┌─────────────┴─────────────┐
     ClaudeAdapter               CodexAdapter
  UUID/父链/sidechain        response/event/turn/lineage
  content blocks/compact    compact/rollback/history mode
         └─────────────┬─────────────┘
             VersionedFileStore
     原始行 + 定位 + 备份 + 冲突检查 + 写后验证
                       │
          各引擎所需的索引 / 元数据适配
```

### UI 和写入模型必须分开

建议核心对象包含：

- `SessionRef`：引擎、session ID、根目录及来源格式；不能沿用 OpenCode 的 `ses_` 前缀假设。
- `RawRecord`：原始 bytes、物理行/偏移、解析结果、未知字段和诊断。
- `MessageProjection`：用于展示的角色、正文、工具、思考、时间与元数据。
- `EditTarget`：所属 snapshot revision、源文件、记录身份及 JSON Pointer；没有稳定消息 ID 的旧格式需要版本绑定的物理定位。
- `MutationPlan`：目标字段、关联副本、涉及文件、派生更新和预期不变量。
- `VerificationResult`：分别记录写盘、结构、冷恢复及请求核验结果。

不要把展示时拼接的字符串直接作为 `message.content` 的替代物，也不要将“重复 UUID”统一判成应全部修改或只取第一条；应由引擎版本定义其记录更新语义。

### 各项目取其哪些长处

| 来源 | 适合提取/借鉴 | 不建议带入 |
|---|---|---|
| coldxx | turn/record 双视图、Codex editable target 映射、备份清单、临时替换模式 | 巨型内嵌 UI、按文本相等的唯一关联依据、宽泛递归 replace、远程 rewrite 功能捆绑 |
| llm-lens | Claude 项目发现、子会话导航、文本转换、链关系诊断思路 | 扁平 content writer、隐式删结构块、普通编辑直接覆盖 |
| didvc | 简单内联编辑和明确保存入口 | 整文件浏览器快照作为保存协议 |
| Tauri Manager | 操作计划界面、索引/侧栏诊断、app-server 读取对照 | 未落地的恢复链、固定 SQL schema、多步写完即报成功 |
| VS Code 扩展 | 流式首行改写、Provider 差异检测、轻量文件读取 | IDE 宿主耦合、缺失备份的 mutation、把启发式状态修复当通用恢复 |
| CSM | 从公开机制研究 raw/effective history 的区分 | 未明确许可的代码与未固定 Codex commit 的大依赖 |
| Codex 官方源码 | 有许可前提下参考/提取版本化重放、lineage、类型和测试规则 | 把 main 分支实现当稳定外部 API；忽略 Apache-2.0 及 NOTICE 要求 |
| es6kr | 独立 Claude Core、类型感知 target 选择、Web/MCP/VS Code 工程组织 | 不修复就沿用直接覆盖、首块限制和重复 UUID 读写差异 |
| XiaoZhi | 字段 locator、preview/apply/restore、目标锁与投影管理的设计 | 在无许可情况下复制代码；把 Windows 实现视作 macOS 已可用 |
| session-porter | AgentAdapter 边界、显式跨引擎迁移 | portable→native 重建作为无损编辑；把 best-effort 注册视作 resume 保证 |

也可以复用我们此前 `opencode-chat-history-editor` 的 React/MUI **界面与交互**：完整片段展示、会话 ID、搜索跳回上下文、编辑弹窗和备份列表。其 SQLite 表结构和官方 Part PATCH 后端不能照搬到这两个新引擎。

### 技术栈建议

底层仍优先 **TypeScript + Node.js 本地服务**，方便整合 es6kr Core 与 coldxx 思路。若继承 es6kr 全工程，则使用其 SvelteKit 生态；若只需本地 Web 并保持现有体验，可以继续用 React/MUI。是否换前端框架不应与是否复用 Claude Core 绑定，更不必为此同时启动 Flask 后端。

如后续需要桌面安装包，再评估 Tauri 包装。若对 Codex 某个复杂格式确需原生 Rust 重放，可做固定版本的独立 helper，而不是第一天把整个 `codex-core` 编入全部功能。

## 七、第一版范围与实现顺序（建议，尚未实现）

### P0：先建立可验证的存储边界

能力探测、原始记录保真、版本绑定定位、备份恢复、并发追加检测、失败注入。为普通/压缩/共享前缀/未知格式分别给出明确状态，不静默忽略不支持的会话。

### P1：完成两引擎最小可用编辑

- 发现会话与完整浏览，保留未知记录查看入口。
- 对明确支持的本地、非活跃、无共享前缀的格式，编辑指定 user/assistant **text block**。
- 保留同条消息中的其他块、后续记录、身份和原生成 usage。
- 显示变更预览、写后复读与可恢复版本；不自动重跑模型。
- 完成搜索定位、会话 ID 复制及原始记录定位。

这里的“非活跃”包括需要冷恢复的已加载状态，不能只看最近十分钟是否改过文件。

### P2：覆盖恢复语义的困难情况

压缩检查点与有效窗口、多重消息表示、重复 UUID、工具配对、Claude 分支/sidechain、Codex paginated 与共享前缀、压缩文件、需要更新的索引。每增加一个格式能力，都补对应版本的隔离用例。

### P3：再加入管理增强

删除、fork、截断、原生回退、Provider 迁移、归档、索引修复。每个功能单独命名和预览，避免把删除/回退冒充保留后续的编辑，也避免自动修改所有无关状态文件。

对签名或加密 reasoning，第一版以保留和展示为主；不能声称可以还原没有保存的思考或重新签名。用户/助手正文编辑是本次优先交付目标。

## 八、必须正面解决的三个难点

### 并发与原子写

备份、文件内目标字段修改、同目录临时文件、权限保持、fsync、提交前版本复查及提交后核验应组成实际保存路径。多文件/SQLite 更新需要可恢复操作日志和明确失败补偿。

但不能承诺“加一个 hash 就彻底解决并发”：官方进程不一定遵守编辑器的锁，检查与 rename 之间也有窗口。对无法协调的活动会话，应先阻止写入并提示关闭/卸载后再操作。

### 修改位置与有效上下文

同一段话可能在事件投影、模型历史项和压缩快照里出现。不能做全文件字符串替换，也不能假定改了显示来源就改了恢复来源。共享历史引用还要求区分逻辑 thread 与物理 rollout，必要时采用经过验证的 copy-on-write 方案。

### 保留后续不等于重算后续

如果把前面的“采用方案 B”改成 C，后面已经生成的“按 B 实现”仍会保留。编辑器应忠实呈现这一结果，不自动编造新的后续回答，也不把这种语义不一致解释成文件保存失败。

## 九、本轮证据与验收范围

| 来源 | 子 Agent 报告的实际验证 | 没有证明的部分 |
|---|---|---|
| llm-lens | Flask stub 下调用实际 mutation 函数，合成链/工具孤儿/坏行/嵌套假成功 | 完整 HTTP/UI、官方 Claude 恢复 |
| coldxx | 核心编辑函数的合成 rollout 验证、备份和后继检查、语法检查 | 官方各版本生成格式及恢复请求 |
| didvc | 解析/编辑算法合成复现、语法检查；服务启动因缺 Express 停止 | HTTP 写回、浏览器及官方恢复 |
| CSM | Cargo metadata/快照检查 | 实际构建与原生操作；部分测试 fixture 不在仓库 |
| Tauri Manager | 35 项 JS 纯函数测试 | Rust mutation、恢复/导入执行、官方 resume |
| VS Code 扩展 | VM + vscode stub + 合成 SQLite/rollout 的管理操作测试 | 真实 Extension Host、官方 resume 和模型输入 |

主 Agent 本轮读取六份报告并复核关键源码调用点、8 个仓库 HEAD 与工作树；没有重复执行上述测试，没有安装大型依赖或发起真实模型请求。Codex 官方重放测试本轮仅阅读，未运行。

**正式产品的下一道关键验收**是固定 CLI 版本，用隔离目录与 mock transport 验证：编辑目标写回后，冷恢复的下一次请求确实包含预期的新正文，同时保留预期后继。现阶段不能把这一结果写成“已经通过”。

## 十、最终建议

第二轮修订为 **“优先验证 es6kr 的 Claude Core/界面 + coldxx 的 Codex 编辑思路 + 自行实现版本化 projection/共享锁适配 + 共享可靠写入层”**。XiaoZhi 用作设计对照，session-porter 用作迁移/Adapter 参考；llm-lens 与原有管理工具降为辅助参考。

统一的是界面、定位、变更计划、备份和验证框架；Claude 与 Codex 的存储/恢复语义各自独立实现。CSM 可用于理解重放，但许可未明确前不复制其实现；优先对照有明确许可的官方 Codex 源码。

**不建议原样拼接六个项目，也不建议直接把 llm-lens + coldxx 并排运行就宣布完成双引擎编辑器。** 它们提供了足够的实现参考，但格式保真、活动会话协调、压缩/共享历史和恢复验证，仍是新项目必须承担的核心工作。

新增 `CodexProjectionManager` 不是剩余工作的全部。即使保留同一 thread ID 并重建 UI 投影，也还需要验证模型有效窗口、共享前缀和冷恢复。详细修订依据见第 09 份报告。
